# 锻造/合成 · 装备呼吸发光（原版 `SetRenderBlinkColor`）

> 2026-09-23。自机与远端的武器/盾随**锻造等级(Aging)/合成(Craft)** 呼吸发光的实现说明。
> 逻辑在 `src/game/agingBlink.ts`（无 three 依赖），渲染在 `src/render/blink-fx.ts`。

## 1. 原版做了什么（四步链路，都有出处）

| # | 位置 | 做了什么 |
|---|---|---|
| ① | `playsub.cpp:834-843`（主手）/ `:891-899`（副手）/ craft 在 `:848-866`/`:905-923` | 装备时按 `ItemKindCode` + `ItemAgingNum[0]` 取一行色表，写进 `sColors[R/G/B/A]`，并把 `ColorBlink` 置 **9** |
| ② | `playsub.cpp:771-786` `GetItemKindFromBliankColor` | 用 (r,g,b,a) **反查**同一张表拿 `TexMixCode`/`TexScroll`（原版之所以要反查：`sColors` 也可能来自物品的 `EffectColor`） |
| ③ | `character.cpp:6596-6659` `SetRenderBlinkColor` | 每帧算三角波，把 `(bTime*R)>>9` 加进 `smRender.Color_R/G/B`；`TexMixCode >= 0` 时 `SetItem2PassTexture(...)`；用完 `RestoreRenderBlinkColor` 撤销 |
| ④ | `smRend3d.cpp:2044/2066` `AddLight(...)` | 那个颜色是**加在顶点光上**的（贴图被 `光照 + 表色×波形` 调制）⇒ 视觉 = **网格上叠加一层呼吸的彩色光** |

第二通道（叠加贴图）的渲染：`NewSourcePT-2023/SrcGame/src/smLib3d/smRend3d.cpp:3311-3360`
（stage0 = `MODULATE`、stage1 = **`ADD`**，即"底图 × 顶点光 + 叠加贴图"），
UV 横向滚动公式在 `:2859`/`:2974`（`wtime = (RendStatTime>>6)&0xFF; fwtime = wtime/256; U = u + fwtime*(state-4)`）。

### 数值口径（照抄，别"顺手优化"）

- **周期 1024ms**：`Blink = 9` ⇒ `BlinkTime = 1<<9 = 512`、`BlinkMsk = 511`；
  `bTime = dwPlayTime & 511`，第 9 位落 = 升半波、不落 = 降半波。`dwPlayTime` 是**毫秒**
  （同文件里 `dwPlayTime + 60*1000` 当 60 秒用）。峰值是 `511/512` 而**不是 1**。
- **相位**：原版是"先降后升"（t≡0 为峰）。两处实现必须同相 —— 见 `blinkWave()` 的注释。
- **等级 → 行**：aging **4..20** → 行 0..16（1..3 与 >20 没有表项）；craft 的 `ItemAgingNum[0]`
  是**材料槽+1**（`sinTrade.cpp:5008`）⇒ **0 → 行 0、6..10 → 行 1..5、其余不发光**。
- **A 列恒 0**：原版 `SetRenderBlinkColor` 的两条 alpha 分支（`a<0` / `a>0`）在这张表上都不成立。
- **叠加贴图表**：`0..4 = mixS_01..05`、`5..9 = mixM_01..05`（`smRend3d.cpp:34-38`，与同仓库
  服务端副本 `ScrServer/.../smRend3d.cpp:36-40` 逐字相同）。⚠ `SrcGame` 那份被私服改成了
  `mixM_01..14` 且色表多出两行取值 256/768（永不命中）—— **不采信**，理由写在
  `mixOverlayTexture()` 的注释里。

### 一处错误模型的更正（重要）

早前有一版把它当成"**乘性 alpha 蒙版 + 布尔旁路闸门**"，并造了 `uBlink{alpha,active,rgbAdd}` 的
着色器模型。**源码里没有这回事**：`uBlink` 在 ex-machina / NewSourcePT-2023 / PristonTale-EU
三个仓库里都搜不到（是自造命名）；表里 A 列恒 0；`ColorBlink=0` 只表示"这件装备没有闪烁效果"。
真正的可见量是**加性彩色光**（第 ④ 步）+ 有 `TexMixCode` 的条目才有第二通道。
这一版按源码重写：用 `emissive + emissiveMap` 复刻"贴图 × (光照 + 表色×波形)"，逐项同构。

## 2. 我们的实现

```
game/agingBlink.ts    ← 纯逻辑：表行、等级→行、三角波、叠加贴图名、滚动量 + `blinkRowOfAppearance`
render/blink-fx.ts    ← 渲染：BlinkFx（材质发光 + 第二通道叠加网格），自机/远端/副手/选角预览**同一份**
render/weapon-rig.ts  ← **装配层**：WeaponRig（主手 + 副手 + 两件各自的 BlinkFx + 姿态 + 生命周期）。
                        `loadAndMount(root, 外观, 姿态, { anisotropy, isAlive, label })` 是**唯一入口**；
                        自机 / 远端 / 选角预览都只做"建 rig → 调它"
ui/WorldView.ts       ← 挂载点：`selfRig` / `actor.rig`；renderLoop 每帧 `rig.updateBlink(rafMs)`
ui/CharSelect.ts      ← 选角预览：`previewRig`（同一个类），`startRenderLoop` 每帧推进
main.ts               ← proto 外观 → 客户端外观（`mapAppearance`，一份）；自机再用**本地物品表**
                        覆盖那四个字段（`withSelfBlink`）并订阅物品变化重推
game/weapon-set.ts    ← W 切武器套的乐观预测也把发光输入一并给全（否则那一个往返里会沿用旧武器颜色）
```

**为什么发光要有"装配层"**：原版这段就在 `sinSetCharItem` 里（跟"挂哪个模型"同一个函数），
而它的顺序有两条硬规矩 —— **发光必须先于挂载**（叠加层挂在网格子节点上，镜像份是 `mount()` 里
`clone()` 出来的，晚建镜像那份就没有叠加层）、**守卫要在每次 await 之后**（否则过期的那次装配
会把旧武器留在骨上）。这两条以前在三个调用点各写一遍，已经漂移过一次（副手缺骨时：
游戏内退到左手、选角页不显示）。现在只有 `WeaponRig` 一处。

**挂载不回退**（用户 2026-09-23："装备在哪个手应该是确定性的，为什么需要回退？！"）：
`WeaponMount` 原来那条 `指定骨 → 右手 → 左手` 的链**已删**；副手同理。取不到目标骨 = **不挂**
+ `reportFallback`（可见）。依据同原版 `SetPattern`（`GetObjectFromName`，取不到即 NULL）。

**骨架专属的手部挂点**（同一个"确定性"原则的另一半）：通用右手骨是 `Bip weapon01`，但
`m1..m7.smb` 有、**只有第 11 职业·格斗家的 `m8.smb` 没有**（逐文件实测；m8 有 `Bip01 R/L Hand`、
`Bip01 L Forearm`、`Bip in01/in-bow/in-cro`）。格斗家是徒手职业，武器（拳套 WV1xx）与其它武器
都戴在手上 ⇒ `weapon-loader.ts` 的 `HAND_BONE_BY_SKELETON` 里**显式登记** `'m8.smb' → 'Bip01 R Hand'`。
⚠ 这是**数据映射，不是回退链** —— **只换骨名、不换手**；表外骨架而通用骨也缺 ⇒ 不挂 + 上报。
（副手盾走 `Bip01 L Forearm`，m8 里本来就有 ⇒ 与骨名无关。）

服务端（`jpstale-server`）：
```
modules/protocol/.../base/common.proto   ← CharacterAppearance 加 4 个 int32（14..17）
modules/common-model/.../CharacterAppearance.java   ← 四个字段（纯模型，被 common-service/web-server 可复用）
apps/game-server/.../AppearanceService   ← EquipEntry 带上实例的 kindCode/agingNum；derive 填进外观；
                                            recalcAndBroadcast = 「重算 + 只在 equals 变了才广播」唯一实现
apps/game-server/.../AppearanceCodec     ← 上线（无条件 set，与既有风格一致）
apps/game-server/.../AccountService      ← 选角/登录那条路从 userdb.item 实例行取这两列
apps/game-server/.../AgeEffectBroadcaster ← 锻造升级后补一次外观广播（战斗养那条路没有 refreshPlayerStats）
```

- **唯一输入是"外观"**：`CharacterAppearance` 上四个字段
  （`weaponKindCode/weaponAgingLevel/offHandKindCode/offHandAgingLevel`，= 原版 `ItemKindCode` + `ItemAgingNum[0]`）。
  服务端**只发原始事实、不持有色表**（色表只在客户端 `src/game/data/aging-blink.generated.json` 一份）。
- **自机以本地物品表为准**：`withSelfBlink` 用本地装备覆盖那四项（锻造刚 +1 时服务端的包可能还没到）；
  远端**只用**服务端下发 —— 所以 `withSelfBlink` 绝不能用在远端身上（那会把我的装备塞给别人）。
- **发光与模型指纹各判各的**：`applySelfAppearance` 先更新发光（便宜、同步），再看
  `appearanceModelKey` 决定要不要重建模型。发光**不进指纹** —— 进了的话每次锻造升级都会重播动画。
- **服务端"变了才广播"**：`CharacterAppearance.equals` 逐字段比较，所以"只有锻造等级变了"也会广播
  （这正是旁观者能立刻看到换色的前提）；而整理背包这类高频入口不会产生无谓广播。
- **上下线顺序无所谓**：proto3 新字段对旧端是未知字段（忽略），旧服务端不下发 ⇒ 新客户端那四项为 0
  ⇒ 不发光。两边各自升级即可。
- **选角界面**（`CharSelect`）用的是同一套：外观同样带那四个字段（服务端角色列表里就发），
  预览的指纹 `appSig` 也把"副手 + 四个发光输入"算进去 —— 否则"只差一面盾 / 只差锻造等级"的
  两个角色会被判成同一个外观而不重载（那正是"选角页看不到盾/看不到光"的一半原因）。

- **发光怎么落到材质**：`material.emissive = 表色/255 × 波形`、`emissiveMap = 该武器自己的贴图`。
  three 的片元 = `贴图×光照 + 贴图×emissive` —— 与原版 `贴图 × (光照 + 表色×波形)` 同构。
  ⚠ **不要改用 `material.color`**：color 是乘在光照之前的，加到它上面等于连光的强弱一起改了。
- **第二通道**：与原网格**共几何、挂在原网格子节点**、加色混合、不写深度的第二层网格。
  挂子节点的好处：变换/可见性/**镜像克隆**（刺客匕首那把）全部自动跟随。
- **贴图偏移写在 `texture.offset`**（不是材质 uniform）⇒ 按 `(TexMixCode, TexScroll)` 缓存
  **私有副本**，否则两把用同一张 mix 贴图的武器会互相踩。
- **镜像份**：叠加网格在 `mount()` 之前建好 ⇒ 刺客匕首 `clone()` 出来的镜像份带上了它；
  three 的 `clone()` 共享材质 ⇒ 两把一起呼吸（`verify-blink-fx` 钉住这条）。
- **缺贴图不静默**：走 `reportFallback('blink', …)`，表现是"该件只有呼吸光"，信息框/降级清单可见（AGENTS #12）。

## 3. 已知缺口 / 待办

1. **+21 以上没有呼吸光**：表只到 +20（照抄）。我们的锻造可以到 +30（见
   `docs/锻造与合成-我们的实现方案.md`）⇒ **+21 以上没有呼吸光**。要的话得先定色（我们的决定，
   不是原版的），那是一项独立决定，别顺手外推。
2. **`BlinkScale`（发光时模型缩放）未实现**：原版 `SetRenderBlinkColor` 的返回值会乘到
   `BlinkScale` 上做网格缩放，来源是 OpenItem 的 `ScaleBlink`（我方没有这一列）——
   锻造/合成分支本身不设它（只设 `ColorBlink`），故当前**无来源**、不做。
3. **`EffectBlink`/`EffectColor` 路线未接**：原版普通装备也能靠物品自身的这两列发光
   （`ColorBlink != 0` 的分支）。我们没有那两列的数据，`findBlinkRow()` 已留好入口。
4. **`aging_num` 对合成物的语义**：我们的合成**不写** `aging_num`（配方 id 记在 `aging_num2`）
   ⇒ 合成物恒为 0 ⇒ 走色表行 0。原版那几行（agingNum 6..10 → 行 1..5）在我们库里不会出现；
   要让合成物按材料槽换色，得先决定"要不要把材料槽也存下来"（那是改数据，不是改渲染）。
